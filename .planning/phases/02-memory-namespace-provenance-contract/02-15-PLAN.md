<objective>
Close the 5 info-level findings — non-blocking polish items that improve code clarity, observability, and configurability without changing user-visible behavior:

- **IN-01 (info):** `decomposeDocId` calls `parseDocId(docId)` on every invocation as defensive re-validation. Since `DocId` is branded and the input is valid by construction, this is a micro-cost on the hot path (`findSinkContaining` invokes it per registered sink per validator call). Either remove the defensive call OR document it as `@internal` defense against test-time `as DocId` smuggling.
- **IN-02 (info):** `__clearContractCache` is freely exported from `src/memory/contract/index.ts` and re-exported through `src/memory/index.ts`. Production code can call it and wipe the cache. Move to a deep-import-only `__testing__.ts` module; remove from the public barrel.
- **IN-03 (info):** `memory-stats` aggregates `by_type` / `by_status` by scanning rows returned from `listByPathPrefix(prefix, 10_000)`. A sink with >10_000 docs sees `doc_count: 12_345` but `by_type` sum = 10_000 — arithmetically inconsistent. Emit a `truncated: true` marker so clients can detect the cap.
- **IN-05 (info):** `discoverMemorySinks` hardcodes the folder name `_memory` (line 105 of `src/server.ts`). Surface the convention as an exported constant `MEMORY_AUTO_DISCOVERY_FOLDER` so the magic isn't buried in a string literal; behavior unchanged but the convention is documented.

In scope:
1. **IN-01:** Pick the lighter option — keep the defensive `parseDocId(docId)` call but annotate it `@internal` with a comment explaining the cost vs safety trade-off. Add a perf note that mentions the hot-path concern for future optimization. Don't remove the safety unless we have a measurement showing it's a real bottleneck. (REVIEW.md itself says "Acceptable for safety but worth noting"; pick the documented-with-comment route.)
2. **IN-02:** Create `src/memory/contract/__testing__.ts` exporting `__clearContractCache`. Remove the export from `src/memory/contract/index.ts`. Update all test files that currently import via the public barrel to use the deep path.
3. **IN-03:** Add a `truncated?: boolean` field to `MemoryStatsEntry`. In `readMemoryStats`, when the row count from `listByPathPrefix(prefix)` equals the default cap, set `truncated: true`. Export the cap as a constant from `src/db/queries/notes.ts` so the resource and any future caller agree.
4. **IN-05:** Add `export const MEMORY_AUTO_DISCOVERY_FOLDER = "_memory" as const;` at the top of `src/server.ts` (near `discoverMemorySinks`). Replace both literal occurrences (`"_memory"` and `"obsidian-fs://${v.name}/_memory/"`) with references to this constant. Update the function's TSDoc to mention the constant.

Out of scope:
- Changing `findSinkContaining` to memoize. The hot-path cost is documented; the actual fix can wait for a perf-driven follow-up.
- Re-architecting `__clearContractCache` to be unnecessary (e.g., making the cache vault-scoped instead of process-global). That's a Phase 5/6 concern per the existing TSDoc.
- Migrating `by_type` / `by_status` to SQL `GROUP BY` with `json_extract`. Lower change-surface route picked instead.
- Making `discoverMemorySinks` scan for ANY folder containing `.memory-sink`. The explicit-config route via `[[memory_sinks]]` already covers that use case; this plan just surfaces the auto-discovery default name.
</objective>
