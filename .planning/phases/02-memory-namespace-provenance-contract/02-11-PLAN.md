<objective>
Close **CR-03 (critical):** `joinVaultPath` and `pathInSink` use `node:path.join`, which on Windows emits backslash-separated paths. Downstream comparisons in `findSinkContaining`, `lastMemoryWriteAtForPathPrefix` (SQL `LIKE '_memory/%'`), `countByPathPrefix`, `recall`'s `notePath.startsWith`, and the auto-discovery probe all assume forward-slash. The DocId resource is always forward-slash (by `DOC_ID_PATTERN` invariant), so the mismatch turns the Phase 2 guard chain into a silent no-op on Windows.

The substantive fix lives at the seam: `path.ts` becomes the single point where vault-relative paths are minted, and it ALWAYS emits forward-slash for any value that will be compared against a DocId resource, a SQL `notes.path` row, or a `findSinkContaining` lookup. OS-native separators stay confined to absolute on-disk paths that FS calls actually consume.

In scope:
1. Refactor `src/adapters/delivery/obsidian-fs/path.ts`:
   - Rename the existing `joinVaultPath` (or keep the name; the README in REVIEW.md suggests renaming) — the IMPORTANT change is the contract, not the name. Pick: keep `joinVaultPath` as OS-native for FS callers (it produces absolute paths), and ADD a new `joinVaultPathPosix(...segments: string[]): string` that always emits forward-slash for vault-relative use.
   - Keep `pathInSink(vaultAbsolutePath, sink, relativeSubpath)` for FS callers; it stays as `path.join` (OS-native absolute) because the only consumers are `fs.access` / `fs.readFile` / `fs.writeFile`.
   - Add a new `vaultRelativeInSink(sink, relativeSubpath?)` (or equivalent name) returning the forward-slash form of `<sink.resolveToRelativePath><relativeSubpath>` for any caller that compares against a DocId resource or feeds a SQL `LIKE` prefix.
2. Add explicit TSDoc to each helper documenting WHICH consumers each is for (FS vs comparison/SQL). Lock the contract so future readers cannot accidentally pick the wrong one.
3. Author `src/adapters/delivery/obsidian-fs/path.test.ts` (extend if it exists) with cross-platform assertions:
   - Round-trip: `vaultRelativeInSink({resolveToRelativePath: "_memory/"}, "observations/foo.md")` returns `"_memory/observations/foo.md"` regardless of OS.
   - Backslash-rejection or normalization: input containing `\\` is either normalized to `/` or refused (decide via TSDoc; the test asserts whichever direction is chosen).
   - Match property: the output of `vaultRelativeInSink(sink, subpath)` is byte-equal to the resource portion of `formatDocId("obsidian-fs", vault, vaultRelativeInSink(sink, subpath))` — proves round-trip with the DocId resource form.

**Why not fix `path.join` directly to `path.posix.join` everywhere?** Because `pathInSink` returns an ABSOLUTE path that goes into `fs.access`/`fs.readFile`, and Windows `fs` reliably accepts forward-slash absolute paths starting with a drive letter, but the convention is OS-native. Splitting the helpers keeps the FS path absolute+OS-native and the comparison path relative+forward-slash. This is the cleanest version of REVIEW.md's recommended fix (variant a vs b).

Out of scope:
- Auditing all consumers in this plan — Plan 02-14 (WR-08) will thread `findSinkContaining(docId)` through audit-row stamping. The auto-discovery probe in `src/server.ts` already constructs its path manually (see `sentinelExistsAt` in `sentinel.ts` lines 174–188 — it uses explicit `/`) so it's already forward-slash and doesn't need this plan's changes.
- Changing `notes.path` storage semantics in the DB. The indexer already writes forward-slash by convention; verify via grep in the verification step.

    **Step 1 — rewrite `src/adapters/delivery/obsidian-fs/path.ts`:**

    Keep the existing `joinVaultPath` and `pathInSink` signatures intact (no consumer changes needed — they are FS-bound). Add the two new helpers:

    ```ts
    import path from "node:path";

    // Existing helpers — OS-native, FS-bound. KEEP AS-IS.
    export function joinVaultPath(vaultRoot: string, relPath: string): string {
      return path.join(vaultRoot, relPath);
    }

    interface SinkLike {
      resolveToRelativePath: string;
    }

    export function pathInSink(
      vaultAbsolutePath: string,
      sink: SinkLike,
      relativeSubpath = "",
    ): string {
      return path.join(vaultAbsolutePath, sink.resolveToRelativePath, relativeSubpath);
    }

    /**
     * Vault-relative POSIX join — emits forward-slash regardless of `process.platform`.
     * Use this for ANY value that will be compared against a DocId resource, used
     * as a SQL `LIKE` prefix against `notes.path`, or threaded into
     * `MemorySinkRegistry.findSinkContaining` lookups.
     *
     * On POSIX this is functionally equivalent to `joinVaultPath` minus the leading
     * vault root; on Windows it differs because `path.join` would have emitted
     * backslashes that downstream forward-slash comparisons miss (CR-03).
     */
    export function joinVaultPathPosix(...segments: string[]): string {
      return path.posix.join(...segments.map(normalizeToForwardSlash));
    }

    /**
     * Forward-slash form of a path INSIDE a sink, relative to the vault root.
     * Used for any caller that compares against a DocId resource (always forward-
     * slash by `DOC_ID_PATTERN` invariant) or feeds a SQL `LIKE '<prefix>%'`
     * lookup against `notes.path` (forward-slash by indexer convention).
     */
    export function vaultRelativeInSink(
      sink: SinkLike,
      relativeSubpath = "",
    ): string {
      if (relativeSubpath === "") return normalizeToForwardSlash(sink.resolveToRelativePath);
      return joinVaultPathPosix(sink.resolveToRelativePath, relativeSubpath);
    }

    /**
     * Defensive: convert any backslash to forward-slash before joining. Inputs
     * are normally byte-clean (sink handle parser at `src/memory/sink.ts`
     * refuses backslashes inside segments), but `relativeSubpath` may originate
     * from caller-controlled inputs — normalize for safety.
     */
    function normalizeToForwardSlash(s: string): string {
      return s.includes("\\") ? s.replace(/\\/g, "/") : s;
    }
    ```
