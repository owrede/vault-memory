<objective>
Land the **memory-read slice** — the third and final memory tool, `recall`. This is the read-side counterpart to `record_observation` and `supersede`; together the three primitives complete MEM-02/MEM-03/MEM-04 — the user-facing memory CRUD.

This plan depends on **02-02 (substrate)** AND **02-04 (record_observation/supersede)** for two reasons:
1. Substrate (MemorySinkRegistry, decomposeDocId, CitationPacket precursors) comes from 02-02.
2. 02-04 modifies the same set of cross-cutting files this plan touches (`src/server.ts`, `src/tool-registry.ts`, `src/tool-registry.test.ts`, `src/server.test.ts`, `src/memory/tools/index.ts`, `src/memory/index.ts`). Same-wave parallel execution would conflict on those files — recall therefore sequences AFTER 02-04 (wave 3 vs 02-04's wave 2).

In scope:
1. `src/memory/citation-packet.ts` — define the `CitationPacket` shape exported as the cross-phase contract (Phase 2 recall + Phase 3 assembly tools all consume this). 8 fields per D-01: `{ doc_id, source_handle, title, heading_path, mtime, hash, display_url, properties }`. A `toCitationPacket(doc, displayUrl)` mapper converts a full `Document` (or its read result) into the packet. NOTE: packet `hash` is the read-side `Document.hash` field; this is the correct name on the packet (do NOT rename to `newHash` — that's the write-side `WriteSuccess` field).
2. `src/memory/tools/recall.ts` — `handleRecall(deps, args)` controller. Args per D-01: `{query, min_confidence?, types?, max_age_days?, sink?, limit?}`. Routes through the existing `search_hybrid` service with generous top_k; post-filters to the sink-resolved paths; loads full `Document` properties for each candidate; applies provenance filters; hides `status: "superseded"` by default; sorts `observed_at` DESC with `mtime` tiebreak; then truncates to `limit`.
3. `src/tool-registry.ts` — extend `TOOLS` and `TOOL_SCHEMAS` with the `recall` raw Zod shape.
4. `src/server.ts` — wire the dispatch.
5. `src/server.test.ts` — end-to-end MEM-03 integration cases.

Out of scope:
- Adding `decomposeDocId` to `src/adapters/registry.ts` — that landed in Plan 02-02; this plan only consumes it.
- Adding `include_paths?: string[]` to `search_hybrid` — that is the user-approved fallback if benchmarks show the post-filter is too slow. Phase 2 ships the post-filter approach; the fallback is documented in this plan as a contingency.
- Subscribing to sink-content changes (deferred per CONTEXT.md Deferred Ideas).
- Phase 3 `recency_weight` / `authority_weight` — `recall` adopts those when ASM-07 ships; for Phase 2 the recency signal is the explicit `observed_at` DESC sort.

Honors:
- **D-01**: 8 packet fields are the floor; Phase 3 can extend, but Phase 2 ships all 8.
- Single-resolver rule: sink lookup only via `MemorySinkRegistry`.
- Backwards-compat: `search_hybrid` API signature unchanged — no `include_paths` parameter added in this plan.
- Seam preservation: controller imports no `node:fs|node:path|gray-matter|chokidar`.

Risk note (the contingency): if recall ends up calling `search_hybrid` with `top_k: 200` across a large user vault and post-filtering down to ~5 memory hits, p95 latency could exceed 300ms on a 10k-note vault. RESEARCH §Q7 mitigates by accepting this for v2.0.0 (the 20-doc fixture makes it irrelevant) and naming the fallback explicitly: extend `search_hybrid` with an optional `include_paths: string[]` parameter (purely additive — does not break v1.x callers). We document this contingency in the plan; we do NOT ship it in Phase 2.

    ```typescript
    import type { DocId, Document, SourceHandle } from "../types.js";
    import { decomposeDocId } from "../adapters/registry.js";

    export interface CitationPacket {
      doc_id: DocId;
      source_handle: SourceHandle;
      title: string;
      heading_path: string[];
      mtime: number;
      hash: string;            // read-side Document.hash
      display_url: string;
      properties: Record<string, unknown>;
    }

    /** Build a deep-enough copy of the packet to avoid caller mutations leaking back. */
    export function toCitationPacket(
      doc: Pick<Document, "id" | "source" | "title" | "mtime" | "hash" | "properties"> & { heading_path?: string[] },
      displayUrl: string,
    ): CitationPacket {
      return {
        doc_id: doc.id,
        source_handle: doc.source,
        title: doc.title,
        heading_path: doc.heading_path ? [...doc.heading_path] : [],
        mtime: doc.mtime,
        hash: doc.hash,
        display_url: displayUrl,
        properties: { ...doc.properties },
      };
    }

    /** Construct an obsidian:// display URL from a DocId. Future adapters return the DocId itself. */
    export function displayUrlFor(docId: DocId): string {
      const parts = decomposeDocId(docId);  // from src/adapters/registry.ts (Plan 02-02)
      if (parts.scheme === "obsidian-fs") {
        const vaultParam = encodeURIComponent(parts.authority);
        const fileParam = encodeURIComponent(parts.resource);
        return `obsidian://open?vault=${vaultParam}&file=${fileParam}`;
      }
      return docId;
    }
    ```

The CITATION PACKET shape uses `source_handle` and `mtime: number` — the mapper transcribes accordingly. `heading_path` is a packet-only field (D-01 specifies it); the mapper defaults to an empty array when the doc does not carry one.
