<objective>
Land the **audit discriminator + MCP Resources slice** — the surface-shaping work that distinguishes memory writes from user writes in the audit log (MEM-08) and exposes sink/stats listings as MCP Resources (MEM-09) instead of expanding the tool surface.

In scope:
1. **MEM-08 — audit discriminator.**
   - Migration v9: `ALTER TABLE write_audit ADD COLUMN is_memory_sink_write INTEGER NOT NULL DEFAULT 0;` + `CREATE INDEX idx_write_audit_memory ON write_audit(is_memory_sink_write, at DESC) WHERE is_memory_sink_write = 1;` (partial index per RESEARCH §Q8).
   - `RecordWriteInput` extended with `isMemorySinkWrite: boolean`. `ListWritesFilter` extended with `isMemorySinkWrite?: boolean`.
   - `audit_log` tool input schema gains optional `is_memory_sink_write?: boolean`; output rows gain `is_memory_sink_write: boolean`. The MCP tool `description` string is NOT modified — Phase 1 invariant.
   - Both ObsidianFsDelivery and StubDelivery write paths set the flag at audit-row-write time — derived from whether `opts.sink !== undefined`. `WriteOptions.sink` is the SHARED Phase 1 field that already flows through write/update/delete; no symmetry work needed.
2. **MEM-09 — MCP Resources.**
   - Resources, not tools. `memory_stats` and `list_sinks` are NEW surface; net effect for v2.0.0 is these are added ONLY as Resources, never as tools.
   - URI scheme is FLAT (per RESEARCH §Q4 + CONTEXT.md Discretion default): `vault-memory://memory/sinks` and `vault-memory://memory/stats`.
   - Polled-only (no `notifyResourceUpdated`).
   - Both Resources register through `server.registerResource(name, uri, metadata, callback)` (SDK 1.29 high-level API per RESEARCH §Q4 Code Example).
3. **No changes to v1 tool surface — including description text.** The 23 v1 tools' shapes remain byte-identical, including the `audit_log` description text. The new `is_memory_sink_write` capability is documented in `docs/tools/audit_log.md` and in CHANGELOG, NOT in the tool's MCP description. The optional input field IS allowed (Phase 1 precedent: input-schema extensions with new optional fields are backwards-compatible).
4. **v1-baseline eval invariant.** The existing audit_log invocations the baseline runs MUST return identical payload (modulo the new `is_memory_sink_write: false` field appended to each row — that's the only schema change). Tools/list snapshot at the v1-tool description-text level is unchanged.

Out of scope:
- Audit-row backfill (no historical rows to backfill — v1 audit rows simply default to `is_memory_sink_write = 0`).
- Resource subscriptions (Phase 5/6).
- Per-sink stats endpoints (`vault-memory://memory/sinks/<name>/stats`) — CONTEXT.md explicitly defaults to flat.
- Modifying the MCP `description` text on the audit_log tool — explicitly deferred to CHANGELOG + docs/tools/audit_log.md.

Honors:
- ADR-002 I-1: chokidar stays in `src/adapters/change-feed/`. Resources don't touch the change feed.
- ADR-002 I-2: only the delivery adapter file imports `node:fs`; resource handlers query the DB via the existing Queries classes.
- Single-resolver rule: `list-sinks` Resource asks the registry; no folder walk.
- Backwards-compat: existing `audit_log` callers with no filter get all rows; existing column shape preserved (new column appended, never reorder); tool `description` text unchanged.

Risk note: migration ordering matters. Migration v9 must apply to ALL vault DBs at startup before any new audit row is written. Phase 1's migration runner (in `src/db/database.ts`) already iterates `MIGRATIONS` in order — confirm the new migration is appended (not inserted) so existing v1.x DBs apply it on next open.
</objective>
