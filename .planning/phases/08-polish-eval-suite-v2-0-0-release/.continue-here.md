### 3. UNRESOLVED — Does the Ruleset block `git push origin main`?

This is the highest-priority unknown for 08-08. The Ruleset's `pull_request`
rule type requires PRs to merge into `main`. It's unclear whether the
maintainer (admin) can still push directly to `main` since `bypass_actors:[]`
and `current_user_can_bypass:"never"`.

The v2.0.0-rc.{1,2} dry-runs only pushed tags (refs/tags/*), which the ruleset
does not target. They did NOT test `refs/heads/main` push.

`release.mjs` runs `git push --follow-tags origin main` which pushes BOTH the
commit AND the tag atomically. If the ruleset blocks the heads-ref part, the
whole push is rejected — leaving release.mjs's Phase 5 in a "committed + tagged
locally, not pushed" state.

### 4. Decision options for 08-08's push strategy

To resolve the unknown in (3), 08-08 must commit to one of:

(a) **Just push and see.** Try `git push origin main` as a separate step BEFORE
    running release.mjs. If it succeeds → all 549 commits land on origin/main,

    the work goes public).

(b) **Temporarily disable the ruleset.** Set `enforcement: "disabled"` via
    `gh api -X PUT repos/owrede/vault-memory/rulesets/16599684 -f enforcement=disabled`,
    run release.mjs, then re-enable. Bypasses the unknown entirely. ~30-min gap.
    Solo maintainer; gap is academic.

(c) **Add maintainer as a bypass actor.** Edit the ruleset to allow your account
    to bypass the `pull_request` rule. Test push. Remove from bypass list after
    release. Slightly cleaner than full disable.

(d) **Route v2.0.0 through a PR.** Push everything to a `release-v2.0.0` branch
    (which the ruleset doesn't protect), open a PR, wait for `lint-and-test` to
    pass on the PR, self-approve via a second session (or use `gh pr merge --admin`
    if your account has the auto-merge admin override), then merge. This is the
    "respect the rules" path but adds friction and the maintainer can't approve
    their own PR unless the ruleset's `required_approving_review_count` is set
    to 0 or the PR uses the `--admin` override. Current ruleset requires 1
    approval; a solo maintainer can't satisfy that without changing the
    ruleset OR using `--admin`.

**My recommendation (for the next session):** Start with option (b) — the
cleanest. Disable, push, re-enable. The ruleset's job is preventing accidental
direct pushes to main during normal development, not blocking the explicit
maintainer-driven release operation. v2.0.0 cuts are rare; the ~30-min window
is bounded.
