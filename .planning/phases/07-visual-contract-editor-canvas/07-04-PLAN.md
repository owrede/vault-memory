    resolve-secret: per RESEARCH Architectural Responsibility Map, plaintext resolution is Server-tier — but `safeStorage` is an Electron-renderer API only reachable inside the Obsidian process. Resolution: **the plugin owns ciphertext storage in `data.json`; on a resolve request the plugin reads the ciphertext from its `data.json`, calls `safeStorage.decryptString(...)` IN THE PLUGIN PROCESS, and passes the resulting plaintext to the server tool over the local stdio MCP transport. The server tool uses the plaintext for `${secret:name}` substitution in the active contract instantiation and never logs it.** Input shape: `{name: string, ciphertext: string}` — the `ciphertext` field carries the plaintext-as-of-this-call (the plugin has already decrypted it in-process; the field name is preserved from the prior shape so that the contract is unambiguous about provenance). Output: `{ok: true, plaintext}` on success; `{ok: false, reason: "safe_storage_unavailable"}` when the plugin reports it could not decrypt because the OS keyring backend is missing; `{ok: false, reason: "decrypt_failed"}` for any other plugin-side decryption failure. The `safe_storage_unavailable` case is surfaced as a clean user-facing error in the plugin UI ("Secret '{name}' could not be decrypted on this device — re-enter it in Settings → Secrets"); no plugin-side plaintext-fallback path exists (per CONTEXT D-CHROME-SECRETS, per-device ciphertext is the correct security posture). SECURITY: response payload contains plaintext only — handler MUST NOT include `name` in any log line at level >= info; debug-level logging must redact the plaintext. (Linux `basic_text` `safeStorage` caveat per RESEARCH Pitfall 3 is orthogonal: the plugin still produces ciphertext-shaped values; security posture degrades but the resolution flow is unchanged.)
    set-mcp-client: discriminated-union input. Variant A (add/update): `{name: string, command?: string, args?: string[], env_secrets?: Record<string, string>}` — mutates `[contracts.mcp_clients.<name>]` in `~/.vault-memory/config.toml`; idempotent (re-applying the same input twice succeeds both times); returns `{ok: true, name, action: "added" | "updated"}`. Variant B (remove): `{name: string, remove: true}` — removes the entry; idempotent; returns `{ok: true, name, action: "removed"}`. Variant C (list): `{list: true}` — read-only inventory mode; reads `[contracts.mcp_clients]` from `~/.vault-memory/config.toml` and returns `{ok: true, clients: Array<{name: string, command: string, args: string[], env_secrets: string[], status?: "connected" | "disconnected" | "untested"}>}`. In the list response, `env_secrets` is a key-list ONLY (no values, no ciphertext) — values stay in plugin storage; the server only knows the key names that will be substituted at connect time. `status` is optional and may be `undefined` when the server has no recent connection result cached. Uses `smol-toml` (already in deps) for serialization.
    get-runtime-stats: input `{vault?: string}`; output `{vault: string, notes: number, chunks: number, last_index_at: string | null, embedding_model: string, embedding_dim: number, audit_log_by_kind: Record<string, number>, peer_mcp_status: Array<{name: string, available: boolean}>, contract_count: number}`; vault defaults to the active vault; reads via existing query layers in `src/db/queries/*.ts` — no new DB queries.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| MCP `tools/list` output | Exposes capability surface to all MCP clients of this server |
| `set_mcp_client` writes `~/.vault-memory/config.toml` | Mutates server config from a tool call |
| `resolve_secret` returns plaintext over MCP stdio | Plaintext crosses the MCP transport into the calling client (the plugin) |
| `trigger_reindex` initiates I/O-heavy operations | A misuse could DoS the server |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-04-01 | Elevation of Privilege | New MCP tools (5) | mitigate | Gated by `[plugin] enabled` default-OFF; tool surface unchanged for non-plugin clients; Pattern B (diff-based gating) makes the gate structural, not a runtime check inside each handler |
| T-07-04-02 | Information Disclosure | `resolve_secret` returns plaintext | mitigate | Plaintext never logged at info level; only over local stdio; per RESEARCH §"Security Domain" "Plaintext secret in data.json" + "Cross-contract `${secret:name}` enumeration" |
| T-07-04-03 | Tampering | `set_mcp_client` mutates config.toml | mitigate | Idempotent + structured-output; Zod-validated input; refuses unknown peer-MCP shape; writes atomic via `atomicWriteFile`; the `{list: true}` variant is read-only (no FS mutation) |
| T-07-04-04 | Denial of Service | `trigger_reindex` may be invoked repeatedly | accept | v2.0.0 ships without explicit rate-limiting; plugin UI surfaces busy state; v2.1 can add a rate limiter if needed |
| T-07-04-05 | Tampering | v1-baseline tools-list snapshot drift | mitigate | The gating test asserts byte-identical snapshot under default-OFF; CI snapshot equality test catches any unintended drift |
</threat_model>
