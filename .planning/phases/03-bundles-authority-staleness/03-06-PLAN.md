# Slice 03-06: `assemble_dossier` MCP tool

## Objective

Ship `assemble_dossier({type, key})` — type/key-based document assembly that walks edges and properties to return a structured packet: `{anchor (citation packet), linked_documents (citation packets + relation), property_rollups: {linked_count, linked_types, status_distribution}}`. Strict `properties.type` match (D-03); `key` matches against `title` OR any entry in `properties.aliases` (D-04). In v2.0.0 the `linked_documents[].relation` field is always `"wikilink"` (the only edge type the v1 wikilinks table knows); Phase 4 widens. Closes ASM-10's eval floor.

## Requirements covered

- **ASM-04** — `assemble_dossier({type, key})` walks edges + properties.
- **ASM-05** (partial) — anchor + every linked-document entry carries a full citation packet (D-01 from Phase 2).
- **ASM-10** — ≥5 dossier eval queries on Atlas Robotics fixture at ≥0.8 precision/recall. The existing `_queries/dossier.yaml` already has six; this slice adds two more (alias case, authoritative case) and adds the fixture frontmatter that lets them resolve.

## Approach

**Citation packet contract (M1 fix — single source of truth).** Dossier types are defined in terms of `CitationPacket` imported directly from `src/memory/citation-packet.ts` (8 REQUIRED fields per `src/memory/citation-packet.ts:45-62`, including `properties: Record<string, unknown>` — always populated, empty object `{}` when no frontmatter). Dossier does NOT redefine the packet shape — it intersects `CitationPacket` with dossier-specific extras.

**Response shape (DossierResult):**

```ts
import type { CitationPacket } from "../memory/citation-packet.js";

interface DossierResult {
  // Anchor doc citation packet (the "Alice" doc itself, after type+key resolution).
  // CitationPacket gives all 8 REQUIRED fields (incl. properties); we add ASM-06 optional extras.
  anchor: (CitationPacket & {
    status?: string;
    superseded_by?: string;
  }) | null;  // null when no matching anchor document
  // All docs linking TO the anchor (backlinks), each with a full citation packet + relation tag
  linked_documents: LinkedDocument[];
  property_rollups: {
    linked_count: number;
    linked_types: Record<string, number>;     // e.g. { "Project": 4, "Meeting": 12 }
    status_distribution: Record<string, number>; // e.g. { "active": 5, "done": 8, "unknown": 3 }
  };
  // Structured error when no match found (per D-04). Null on successful resolution.
  error: { code: "no_matching_anchor_document"; type: string; key: string } | null;
}

// Intersection: 8 required CitationPacket fields + dossier-specific extras.
type LinkedDocument = CitationPacket & {
  status?: string;
  superseded_by?: string;
  relation: "wikilink";              // v2.0.0 — widens in Phase 4 (additive change)
};
```

`CitationPacket.properties` is REQUIRED (`Record<string, unknown>`); tests assert `expect(typeof linked.properties).toBe("object")` for every linked document — never `undefined`. The rollup pass reads `linked.properties.type` and `linked.properties.status` directly (no optional-chain fallback needed for `properties` itself, only for the inner keys).

**Algorithm:**

1. **Resolve type+key to anchor doc.** Query candidate notes where `properties.type === args.type`. The v1 path is `query_frontmatter` (`src/server.ts:418`) — re-use the existing tool's underlying function. Walk candidates; first match where `note.title === args.key` OR `args.key ∈ properties.aliases` wins. Deterministic tiebreak: alphabetical `title` then `doc_id`.
2. **If no match:** return `{ anchor: null, linked_documents: [], property_rollups: { linked_count: 0, linked_types: {}, status_distribution: {} }, error: { code: "no_matching_anchor_document", type: args.type, key: args.key } }` per CONTEXT.md D-04 (structured empty, not silent).
3. **Read backlinks** to anchor via `vault.db.wikilinks.listBacklinks(anchor.path)` (or whatever the Phase 1 `src/graph/graph.ts` exposes for backlink lookup; verify which API is canonical). For each backlink note: hydrate `Document` via `SourceConnector.readDocument()`, build the citation packet via `toCitationPacket(doc, displayUrlFor(doc.id, source))` (returns the full 8-field `CitationPacket` including `properties: {}` at minimum), then attach `relation: "wikilink"` plus the optional `status`/`superseded_by` extras when present.
4. **Compute rollups** in a single pass over `linked_documents`:
   - `linked_count = linked_documents.length`.
   - `linked_types`: group by `linked.properties.type ?? "unknown"` (`properties` itself is always an object).
   - `status_distribution`: group by `linked.properties.status ?? "unknown"`.
5. **No superseded filter at the dossier layer.** Dossiers show the whole picture (per CONTEXT.md §"Specifics" — bundles never filter by status; only search does). Superseded backlinks DO appear in `linked_documents` with their `status` field set. Agents that want to filter can do so client-side.

**`authority_weight` interaction (for the new `authoritative-atlas-1` eval query):** the dossier itself doesn't accept ranking params (no `authority_weight` in `AssembleDossierArgs`). The eval is verified by inspecting `result.anchor.properties.authoritative === true` AND verifying that a parallel `search_hybrid({query: "Atlas-1", authority_weight: 1.0})` call ranks atlas-1 above other Project docs. The eval YAML records both expectations.

**Adapter-seam discipline:** `src/assembly/dossier.ts` reads documents only via `SourceConnector.readDocument`. The frontmatter-type query reads from already-indexed `notes.frontmatter` rows in SQLite — that's L0 substrate, fine. No `fs`/`gray-matter`/`path` imports.

**`relation` field caveat (CHANGELOG-flagged):** Per RESEARCH §9 Path 1: v2.0.0 reads backlinks from the v1 `wikilinks` table, which only stores type `"wikilink"`. So every `linked_documents[].relation` is `"wikilink"` in v2.0.0. CHANGELOG entry (per 03-PLAN.md) documents this. Phase 4 GRA-04 introduces typed edges and widens the field. The dossier code should be written so that widening is a one-line change (read `edge.type` instead of hardcoding `"wikilink"`):

```ts
// v2.0.0 (this slice):
relation: "wikilink" as const,
// v2.1.0+ (Phase 4):
relation: edge.type,  // wikilink | mention | frontmatter-ref | hyperlink
```

Leave a `// PHASE-4-WIDEN` comment marker at the hardcoded line so it's easy to grep when Phase 4 lands.

**Performance budget per RESEARCH §"Open Risks" #4:** `assemble_dossier` does an O(N) scan over `notes.frontmatter` for the type match. If this is hot, the v1 `query_frontmatter` tool path already does it without an issue — Atlas Robotics is ~75 notes. Do NOT pre-optimize; if real-world dossier perf is bad, Phase 5 may add a `notes_type` index.
